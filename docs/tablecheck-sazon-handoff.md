# Sazón / TableCheck preparation adapter

Refs #129. Owner: `codex-worker-cbfe5665-79ca-415d-91ac-5c184e516939`.
Stable restaurant: `osm-BAL-sazon`. Shared runtime/server/UI/journal integration
belongs to 32d5; independent source/code review belongs to e98a.

`TablecheckSazon` implements the existing adapter lifecycle (`create`, `current`,
`action`, `remove`, `expire`, `close`). It fetches the exact public venue policy,
performs a narrowly bound Dinner search for two adults, and implements local
selection and review without clicking a native slot or creating a server cart.
The adapter has no submission switch, capability reader, contact transport or
mutation transport. `canHold` and `canSubmit` remain false.

## Native mutation and result boundaries

Pages slot handler 526300 loads the selected menu then invokes the cart helper;
it does not pass the landing branch's skip-cart option. Client helper 3254200
creates `POST /v2/booking/cart` or updates `PUT /v2/booking/cart/:cartId` before
native review. Response includes cart ID, access token and expiry. This is a
server write and capability creation; the exact inventory-hold effect is not
demonstrated. It must not run during a search or an implicitly approved local
selection. Native landing can skip cart to show experience availability, but
that does not make the later slot click safe.

Review pLTq at pages 942610 validates guest, questions and applicable policies;
963576–968500 invokes cart creation/update with final details before checkout.
Final `PUT /v2/booking/checkout/:cartId`, status `PUT /v2/booking/checkout_status/:id`,
cart GET/DELETE, and saved-reservation GET are all denied by this adapter.

The additional chunk resolved an earlier research gap: original completion
code at 90930 distinguishes customer statuses. `confirmed` renders confirmed;
`accepted` renders successfully booked, while pending/request/IOU/cancelled
are distinct. Generic success UI also groups some waiting/attended states,
which must not become a broad confirmation rule. Completion at 103301 reads
`GET /v2/reservations/:code` using the same code and guest email/phone.

A future final verifier must bind the raw response's exact shop, timestamp,
adult/child/baby/senior counts, **all raw orders**, menu quantities and service
category to a durable approved attempt and its own cart and returned code.
Native UI filters unknown menu IDs and normalizes group quantity to one;
neither behavior is suitable for verification. HTTP success, slug, redirect,
checkmark, analytics or `reservation_auto_accept` alone cannot prove success.
No final verifier is exported here because this version cannot originate an
authorized cart/checkout attempt; no unused always-unknown helper is added.

## Shared integration handoff

This is a preparation delivery, not an activation request. Registering the
adapter as current runtime `mode: inspect` permits operator create/current
only: existing runtime intentionally limits inspect actions to refresh. Tests
demonstrate this limitation. **Do not register it as live to unlock search**:
that would incorrectly advertise guest live-booking capability.

32d5 should add a separately reviewed operator preparation action capability
for `search`, `select`, `review`, `refresh`, preserving liveBooking=false and
canHold/canSubmit=false. The adapter uses existing action keys (`date`, `party`,
`slotId`, `revision`). Set entry.current to adapter.current. Its semantic
snapshots have `image:null`; UI must render evidence slots, explicit menu
quantity, category, null-price wording and current policy, not assume a native
form screenshot. The adapter collects no guest details at this stage.
Provider translations contain HTML; render them as text or sanitize them in
the shared UI, never insert unchecked provider markup into the app.

Selection is explicitly local (`selectionSource=local_only_no_native_cart`).
Review fingerprint binds owner, session, exact slot/menu/category and current
policy version; it is a **preparation** fingerprint and cannot authorize final
booking. Selection/review reject evidence older than two minutes. Review
reloads policy and invalidates selection on change. Search invalidates prior
selection before any transport. Owner, revision, busy and ten-minute expiry
guards use the same lifecycle conventions as existing providers.

Before enabling native cart operations, integrate a separate explicit
cart/hold approval and durable journal phase, require reserveSubmission's
`sendAllowed === true` before each authorized mutative dispatch, and retain
exact cart/attempt binding through final consent and saved readback. This
requires shared runtime/journal coordination, not a parallel checkout engine.
The earlier blanket requirement of zero server writes for search was too
broad: ordinary logging/cache/session correlation is not a restaurant hold.

a genuine suitable availability response before end-to-end validation.
