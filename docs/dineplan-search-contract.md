# Dineplan v3 search qualification

The qualification transport `scripts/lib/dineplan-hussar-search.mjs` now performs only the exact Rondebosch page GET and two search POSTs, with a transient cookie jar, twenty-second total timeout, abort support and redirects rejected. It accepts only two guests, checks supplier ID 1068 and an empty booking reference, and returns unknown on errors or ambiguous guest results. It has no seating, contact, payment or confirmation endpoint. Run both test files with `node --test scripts/test-dineplan-hussar-search.mjs scripts/test-dineplan-time-options.mjs` (15 tests; also run by the offline Dineplan CI workflow). A read-only run of this actual module for 26 October/two guests returned sixteen enabled options; its dated result is `data/evidence/dineplan-hussar-module-check.json`. This is not production integration.

Refs #129. This isolated experimental parser and evidence bundle do not activate any restaurant or edit shared provider routing. The canonical integrator and existing release owner retain integration/publication ownership.

The supplier's v3 step1 script populates guests with POST `ajax_covers` and times with POST `ajax_times`. Its time-option callback uses each HH:mm key and the `closed` and `reason` fields. The pure parser conservatively accepts boolean closed flags only. Invalid, rejected, empty or mixed-corrupt responses return unknown with no options. All-disabled options do not establish that the restaurant is sold out. Reasons are untrusted plain text, never HTML.

On 24 October a fresh Hussar Rondebosch form session (supplier 1068) followed by these two search POSTs returned HTTP 200. The form's CSRF value was empty and was sent unchanged; session cookies remained transient and no existing booking reference was used. All 22 time entries had boolean closed flags: sixteen enabled and six closed for online bookings, matching the independently observed native form for 26 October/two guests. `dineplan-hussar-search-projection.json` stores only selected response fields and session-presence booleans, not credentials or a complete raw-response fixture. An additional offline test checks this projection against the native observation. This does not establish behavior for other venues or sessions.

`node --test scripts/test-dineplan-time-options.mjs` exercises synthetic responses, not recorded supplier JSON. Native UI observations are separately recorded in `data/evidence/dineplan-hussar-native.json` and `data/evidence/dineplan-la-colombe-native.json`. Hussar Rondebosch showed sixteen enabled options for 26 October 2026/two guests; La Colombe displayed a calendar-level Fully Booked label before guest selection. No time was selected in either inspection.

`data/evidence/dineplan-v3-boundaries.json` records public script hashes and endpoint intent. It is source evidence, not a server-side side-effect guarantee. Later steps invoke seating and payment lookup; final submission can call confirm or immediate-payment booking creation. Exclude all those paths from initial search qualification. Do not submit contact details, select inventory or follow payment flows during development.

Remaining before production integration: review the isolated transport, adapt it to the shared search contract and registry gate, verify runtime/network compatibility and guest-facing unknown/error semantics. The current evidence qualifies one venue and one dated query only; other Dineplan venues need their own identity, response and policy checks. Keep every registry live flag unchanged. Salsify's calendar application is a different contract. No full supplier confirmation or deployment is verified here.
